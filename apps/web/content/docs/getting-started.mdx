This page takes you from an empty directory to a committed set of config files and a first change applied. Nothing is written to the portal until the last step, and only after you confirm it.

## Before you start

- Node 22.13.1 or later.
- The portal's Hub ID, from the account menu in HubSpot. This page uses `1111111`.
- A Super Admin to create the service key: a key can only hold scopes its creator has. Start on a developer test account or sandbox if you have one.

## Install

In your project directory (run `npm init -y && npm pkg set type=module` first if it has no `package.json`):

```sh
npm install @kalup/core
npm install -D kalup
```

With pnpm, yarn or bun: `pnpm add @kalup/core && pnpm add -D kalup`, and the same with `yarn add` or `bun add`.

`@kalup/core` is what the config files and your app import: builders, codecs and types, with no network and no file system. Your app imports it at run time (7 kB, no dependencies), so it is a regular dependency. `kalup` is the CLI, a dev tool. If you skip the first line, `kalup init` adds `@kalup/core` to `package.json` for you.

The config files are ES modules, so the project should be `"type": "module"`. A CommonJS project with `verbatimModuleSyntax` cannot compile them.

## Create a service key

In HubSpot, open Development > Keys > Service keys ([HubSpot's guide](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/authentication/account-service-keys)) and create a key with, for each object you manage (contacts, companies and deals by default):

- `crm.schemas.<object>.read`, to read its properties and groups. A custom object needs `crm.schemas.custom.read`.
- `crm.schemas.<object>.write`, to apply changes. Leave it out for objects you only read.
- One `crm.objects.<object>.read`, such as `crm.objects.contacts.read`, so `plan` can read HubSpot's property limit. Kalup never reads records with it.

`init` prints the exact list for the objects you pick, and `status` checks the read scopes. [One admin, one portal](/docs/guides/one-portal#create-a-service-key) explains each scope.

Put the key in `.env` in the project directory, or in the environment:

```text title=".env"
HUBSPOT_SERVICE_KEY=<your key>
```

Kalup reads the variable a target names in `credentials.read.env`, or `HUBSPOT_SERVICE_KEY` when it names none. It never prints a key, not even in an error.

## Create the project

```sh
npx kalup init --portal 1111111
```

`init` reads the account behind the key first. When that account is not portal `1111111`, it stops with exit 4 and writes nothing. Otherwise it writes:

- `kalup.config.ts` with one target. The target is named `sandbox` for a sandbox or developer test account and `production` for a standard account, which also gets `protected: true`. `--target <name>` picks another name.
- `kalup/index.ts`, the barrel your app imports.
- The lines `.kalup/` and `.env` in `.gitignore`, created when missing, so history and the key stay out of git.
- A formatter ignore for `kalup/` and `kalup.config.ts`: `!kalup`, `!kalup.config.ts` and `!.kalup` added to `files.includes` in `biome.json` or `biome.jsonc` when one exists, with the file's comments kept, else the lines `kalup/` and `kalup.config.ts` in `.prettierignore` when a Prettier config exists, else a printed note. The writer's format is the only format for those files.
- `AGENTS.md` with the rules an AI agent follows in this project, appended when the file exists.
- `CLAUDE.md` with the one line `@AGENTS.md`, so Claude Code reads the same rules. It is created when missing and appended when it exists, unless it already points at `AGENTS.md`.
- `@kalup/core` in `dependencies` in `package.json`, when no dependency list has it. Run your package manager's install afterwards; `init` does not install it.

Then it runs the first pull. `--objects contacts,companies,deals` is the default scope. A custom object goes in by its name, for example `--objects companies,subscription`. The output starts with the account type, the UI domain and the time zone, the target and its objects, the read scopes the key needs, one per object, with the link to the service key settings, one recommended `crm.objects.<object>.read` scope so `plan` can check HubSpot's property limit (it also lets the key read that object's records, which Kalup never requests), and the files written. The pull summary follows.

`init` refuses to run when `kalup.config.ts` already exists. Run `pull` instead.

The pull writes one file under `kalup/objects/` for each object that has custom properties. A pulled company file:

```ts
import { defineObject, type InferProperties, p } from '@kalup/core'

export const Company = defineObject('companies', {
  groups: {
    billing: { label: 'Billing' },
  },
  properties: {
    billingStatus: p.enum('billing_status', {
      label: 'Billing status',
      group: 'billing',
      fieldType: 'select',
      options: [
        { value: 'active', label: 'Active' },
        { value: 'PAST DUE', label: 'Past due' },
      ],
    }),
    renewalDate: p.date('renewal_date', {
      label: 'Renewal date',
      group: 'billing',
      fieldType: 'date',
    }),
  },
})

export type CompanyData = InferProperties<typeof Company.properties> & { id: string }
```

Each property gets a camelCase key, the builder that matches its HubSpot type, and its full definition when the portal lets you own it. HubSpot-defined properties such as `name` come in only when `include` in [kalup.config.ts](/docs/config/kalup-config) lists them, for example `companies: { include: ['name', 'domain'] }` under `objects`. They come in as references, such as `name: p.string('name')`: no definition, never created, changed or removed. [Config files](/docs/config/config-files) explains the grammar, [Property builders](/docs/config/property-builders) each builder, and [kalup pull](/docs/commands/pull) the scope, the merge rules and the flags.

## When the portal changes

`init` already ran the first pull. Run `pull` again whenever someone changes the portal in the HubSpot UI, or after you change the scope in `kalup.config.ts`, so the files catch up:

```sh
npx kalup pull
```

With one target, no command needs `--target`. A pull with no change in the portal writes nothing. Before a file is overwritten, the old one is copied to `.kalup/history/`.

## Validate

```sh
npx kalup validate
```

`validate` runs offline. It checks `kalup.config.ts` and every file under `kalup/` and reports each problem with the file, the line and a fix. Exit 0 means valid, 3 means invalid. Every other command runs the same checks first, so an invalid project stops before anything is read or written.

Add `--json` to any command for one `envelope/1` document on stdout and nothing else:

```json
{ "format": "envelope/1", "ok": false, "issues": [{ "code": "E_UNKNOWN_GROUP", "message": "...", "file": "kalup/objects/companies.ts", "line": 12, "fix": "..." }] }
```

That is what a script or an AI agent reads. `issues[].fix` says what to do.

## Make a first change

The properties you pulled already exist in the portal, so the first plan adopts them: Kalup records that it manages them, and writes nothing else. Change something in the file first, for example a label:

```ts title="kalup/objects/companies.ts"
    billingStatus: p.enum('billing_status', {
      label: 'Account status',
```

Then save a plan, read it, and apply it:

```sh
npx kalup plan --out plan.json
npx kalup apply plan.json
```

The plan lists each step with what it writes, such as `label: "Billing status" -> "Account status"`. `apply` shows the steps again and asks you to type the target name. It checks the plan against a fresh read of the portal before it writes, and reads each write back. See [kalup plan](/docs/commands/plan) and [kalup apply](/docs/commands/apply).

## Use the files in your app

```ts
import { Company } from './kalup/index.js' // a bundler also resolves './kalup'

const status = Company.properties.billingStatus.get(record.properties)
// 'active' | 'PAST DUE' | Unlisted | null
```

The same file types the property bag, with no generate step. `Unlisted` is a value HubSpot holds that the options do not list yet, such as one an admin added; `.strict()` on the builder throws on one instead. [Types and codecs](/docs/concepts/types-and-codecs) has the details.

## What to commit

Commit `kalup.config.ts`, everything under `kalup/`, `AGENTS.md` and `CLAUDE.md`. The files are the source of truth for the portal, and a change to them is a normal pull request.

Do not commit `.kalup/` (history copies, state, journals and snapshots), `.env` or any other file that holds a key, or the IR. `npx kalup ir` derives the IR from the files whenever something needs it. State stays on your machine; [Sandbox, production and CI](/docs/guides/several-portals) shows how a team keeps it on a branch.

## The other commands

| Command | What it does |
| --- | --- |
| [`kalup ir`](/docs/commands/ir) | Print the `ir/1` document derived from the files. `--check` validates it and prints only issues |
| [`kalup fmt`](/docs/commands/fmt) | Rewrite the files in canonical form and regenerate `kalup/index.ts`. `--check` lists the files that would change, exit 2 with `--exit-code` |
| [`kalup status`](/docs/commands/status) | The config summary, then for each target: key set, portal matches the pin, account type, read scopes present, state |
