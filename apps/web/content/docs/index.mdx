Kalup keeps a HubSpot portal's configuration (objects, property groups, properties and custom object schemas) in TypeScript files in your repository. The same files give your app its types, so a renamed property or a removed option fails at compile time instead of in production.

## What this version does

Sixteen commands, all implemented with offline tests. The package is still at version 0.0.0 and runs from a source checkout. A first live run on one developer test account passed pull, plan, saved-plan apply and drift reconciliation; conformance and release gates remain open. Every command but `apply` only reads a portal; `apply` writes property groups and properties after an approval.

| Command | What it does |
| --- | --- |
| [`kalup init`](/docs/commands/init) | Create `kalup.config.ts`, pin the first target and pull it |
| [`kalup pull`](/docs/commands/pull) | Read a target and write `kalup/objects/*.ts` |
| [`kalup validate`](/docs/commands/validate) | Check the config files and report every issue, offline |
| [`kalup ir`](/docs/commands/ir) | Print the IR document derived from the config files |
| [`kalup fmt`](/docs/commands/fmt) | Rewrite the config files in canonical form |
| [`kalup status`](/docs/commands/status) | Show each target: key, portal check, account, scopes |
| [`kalup compare`](/docs/commands/compare) | Compare config, a target or a snapshot with another |
| [`kalup plan`](/docs/commands/plan) | Show what apply would change on a target |
| [`kalup snapshot`](/docs/commands/snapshot) | Save one read of a target, with what it covered |
| [`kalup docs`](/docs/commands/docs) | Write a Markdown data dictionary of the config or a snapshot |
| [`kalup apply`](/docs/commands/apply) | Apply a reviewed plan to its target |
| [`kalup rm`](/docs/commands/rm) | Take a property or group out of config and write its tombstone |
| [`kalup state rebuild`](/docs/commands/state) | Report what a portal holds against its state, and with `--write` replace the state file |
| [`kalup target rebind`](/docs/commands/state#target-rebind) | Point a target at a recreated test portal or sandbox |
| [`kalup add`](/docs/commands/blueprint) | Write a blueprint into the config files |
| [`kalup blueprint upgrade`](/docs/commands/blueprint) | Merge a new version of a blueprint and keep the client's changes |

`apply` needs one approval: a person at a terminal, `--yes` for a small safe change on an unprotected target, or `--approve` from a reviewed CI job. Every delete needs the person. The first live run covered property/group writes, but the terminal-confirmed delete and real CI workflow still need verification.

Every command takes `--json` and prints one [`envelope/1`](/docs/reference/json-output) document, with fixed [exit codes](/docs/reference/exit-codes).
