`kalup.config.ts` names the project, sets the pull scope and declares the targets. It holds one `export default defineConfig({ ... })` and nothing else. The CLI parses it and never runs it; the `defineConfig` import from `@kalup/core` exists only so your editor type-checks the file. A file that still imports from `kalup` loads the same. `kalup fmt` rewrites the import, as does a command that rewrites the file, such as `kalup target rebind` or a `kalup pull` that changes an override. A plain `kalup pull` leaves it alone.

A field the reader does not know is `E_NOT_DATA` with a list of the fields it does know. The file follows the same grammar as the object files: [Config files](/docs/config/config-files#the-grammar).

## A complete example

```ts
import { defineConfig } from '@kalup/core'

export default defineConfig({
  name: 'acme-crm',
  prefix: 'acme_',
  defaultTarget: 'sandbox',
  objects: {
    companies: { include: ['name', 'domain'] },
    deals: { custom: false, include: ['dealname', 'amount'] },
    subscription: {},
  },
  targets: {
    sandbox: {
      portalId: 1111111,
      credentials: { read: { env: 'HUBSPOT_SANDBOX_KEY' } },
    },
    production: {
      portalId: 2222222,
      protected: true,
      credentials: { read: { env: 'HUBSPOT_PROD_READ_KEY' } },
      overrides: {
        'property:subscription/status': { name: 'subscriptionstatus' },
      },
    },
  },
})
```

- `name` is the project name used in the IR. It defaults to the directory name.
- `prefix` is optional. `validate` warns when a managed property's internal name lacks it.
- `defaultTarget` is the target `pull`, `plan` and `snapshot` use when you pass no `--target`.
- `objects` is the pull scope: which objects, and which of their properties, the files hold.
- `targets` lists the portals this project works with. A target is a named portal, never an environment.

A comment inside `defineConfig` is `E_NOT_DATA`. Only a comment block above the imports is allowed in this file.

`init` writes a smaller version of this file with one target and no `defaultTarget`. See [kalup init](/docs/commands/init).

## Top level

| Field | Type | Default | What it does |
| --- | --- | --- | --- |
| `name` | string | the project directory's name | The project name. It appears as `project` in the IR |
| `prefix` | string | none | When set, `validate` warns (`W_PREFIX`) for every managed property whose internal name does not start with it. A warning never changes the exit code |
| `defaultTarget` | string | none | The target `pull`, `plan` and `snapshot` use without `--target`. It must name a declared target (`E_DEFAULT_TARGET`). It never enters the IR |
| `objects` | map of object name to scope | `{}` | The pull scope, below |
| `targets` | map of target name to target | `{}` | The portals, below |

## objects: the pull scope

Each key is an object name. A standard object uses its HubSpot name (`companies`, `contacts`, `deals`, `tickets`, `line_items` and the others HubSpot lists properties for by name). Any other key is read as a custom object's name, such as `subscription`.

| Field | Type | Default | What it does |
| --- | --- | --- | --- |
| `custom` | boolean | `true` | Pull every property HubSpot did not define |
| `include` | string[] | `[]` | HubSpot-defined properties to pull as well, by internal name |
| `as` | string | PascalCase singular of the key | The export name pull gives the object when it writes the object for the first time. `companies` becomes `Company`, `line_items` becomes `LineItem` by default. An export that already exists keeps its name: rename it in the file |

A portal property is in scope when `include` names it, or when it is custom and `custom` is on. `custom` plus `include` is the only way to select properties. Without a scope, contacts alone hold hundreds of properties, so `init` warns when a first pull writes more than 200 properties for one object.

To see what the portal has outside the scope without writing anything, run `kalup pull --discover`. See [kalup pull](/docs/commands/pull).

## targets

A target is a named portal pinned to a portal ID. Every command that reads a target checks the key's portal against the pin first, and stops before reading anything when they differ.

| Field | Type | Default | What it does |
| --- | --- | --- | --- |
| `portalId` | positive integer | required | The Hub ID of the portal. The wrong-portal guard. Missing or not a positive integer is `E_PORTAL_ID` |
| `credentials.read.env` | string | `HUBSPOT_SERVICE_KEY` | The environment variable that holds the read key. `credentials` needs `read` when present |
| `credentials.write.env` | string | none | Parsed and kept for the release that writes. Unused in this version |
| `protected` | boolean | `false` for a `DEVELOPER_TEST`, `SANDBOX` or `APP_DEVELOPER` account, else `true`, an unknown account type included | Marks a portal where an apply needs a saved plan and a person at a terminal, or a reviewed CI job with `--approve` and a write key only that job holds. `init` sets it for a standard (production) account. `status` reports it, and `plan` records it in the plan and its approval digest |
| `drift` | `'hold'` or `'overwrite'` | `'hold'` | How a plan treats edits made in the HubSpot UI. `'hold'` holds drift and conflicts for a person to settle; `'overwrite'` writes config over them. It needs a base in state: a unit with no base is held either way. `plan` records it in the plan and its approval digest |
| `overrides` | map of address to override | `{}` | Per-target differences, below |

A target may not be named `config` (`E_TARGET_NAME`): `compare` uses that word for the config side. Any other name works, and a name carries no meaning.

`pull`, `plan` and `snapshot` run against one target: the one `--target` names, else `defaultTarget`, else the only target. With several targets and neither, a person at a terminal is asked which one; without a terminal the command stops with `E_TARGET_REQUIRED` and lists the names. [Targets and credentials](/docs/concepts/targets-and-credentials#choosing-a-target) has the full rule.

The key is read from the environment or from `.env` in the project directory, and it is never printed. [Targets and credentials](/docs/concepts/targets-and-credentials) covers keys, scopes and the portal check.

## overrides

An override lets one target differ from the files for one resource. The key is an address that exists in config; anything else is `E_UNKNOWN_OVERRIDE`.

| Field | Type | Used in this version | What it does |
| --- | --- | --- | --- |
| `name` | string | yes, by every command that reads a portal | The internal name this resource has on this target. `'property:subscription/status': { name: 'subscriptionstatus' }` makes pull read `subscriptionstatus` on that target and write it under `status` |
| `skip` | `true` | yes, by every command that reads a portal | Leave the resource out on this target. A skipped group takes its config properties with it |
| `definition` | part of a property or group definition | yes, by `validate`, `plan`, `apply`, `compare`, `pull` and `docs` | Definition fields that differ on this target, below |
| `lookup` | map of string to string | parsed and validated. `plan` blocks the resource and `compare` reports it unknown, since this version manages no lookup resources | Values that differ on this target |

Any other override field is `E_NOT_DATA`.

### definition

A `definition` override states only what differs on this target. Each field it states replaces the shared field whole; the fields it leaves out stay shared.

```ts
overrides: {
  'property:subscription/status': {
    definition: {
      label: 'Contract status',
      description: '',
      options: [
        { value: 'active', label: 'Active' },
        { value: 'paused', label: 'On hold' },
      ],
    },
  },
},
```

- A property may override `label`, `description`, `group`, `fieldType`, `formField` and `options`, and in `lifecycle` each of `options`, `removedOptions` and `ignoreChanges`. A group may override `label`. Anything else, `hasUniqueValue` and `type` included, is `E_OVERRIDE_DEFINITION`, as is an override on a reference, a `.managed(false)` property or a custom object.
- `options` is a whole list: the override's options, in its order, are the target's options. There is no merge by value.
- A field the override states is owned on that target, even an empty value: `description: ''` owns an empty description there, and `options: []` an empty option list.
- An option carries `value`, `label`, `hidden` and `description`. Aliases (`as`) belong to the app and stay in the shared file. An option value the shared options lack is allowed, with `W_OVERRIDE_OPTION`, because the app's codec throws on it.
- The result must pass the rules a shared definition passes: a `fieldType` the builder takes, a `group` of the same object, unique option values, `removedOptions` naming no kept option.
- `plan`, `apply`, `compare` with that target and `docs` use the result. `kalup ir` prints the shared definitions and the overrides as written.
- `pull --target <name>` writes the portal value of an overridden field into the override here, never into the object file, and leaves other targets' overrides alone. A field only the override's `lifecycle.ignoreChanges` names is left to that portal, so `pull` keeps the object file's value; see [`pull`](/docs/commands/pull).

## What this version uses

| Field | Read by |
| --- | --- |
| `name` | `ir` and every command that loads the project |
| `prefix` | `validate` |
| `defaultTarget` | `pull`, `plan` and `snapshot` without `--target`, `validate`, and `status`, which marks it |
| `objects` | `pull`, `init`, `status` (to list the read scopes the key needs), and `plan`, `snapshot` and `compare`, which read the same scope |
| `targets.*.portalId`, `credentials.read` | `pull`, `status`, `init`, `plan`, `snapshot`, `compare`, and `apply` when the target names no write key |
| `targets.*.overrides.*.name`, `skip` | `pull`, `plan`, `snapshot`, `compare` |
| `targets.*.overrides.*.definition` | `validate`, `plan`, `apply`, `compare`, `pull` (which writes it) and `docs` |
| `protected`, `drift` | `status`, `plan` and `apply`, which refuses a plan made under another policy |
| `credentials.write` | `apply`, which sends every request of a run with it |
| `lookup` | Parsed, validated and carried into the IR. No command applies it yet |

Credentials never enter the IR. `kalup ir` shows each target's `portalId`, `protected`, `drift` and `overrides`, and nothing else about it.
