---
title: kalup validate
description: Check the config files offline and report every issue with its file, line and fix.
---

`kalup validate` reads `kalup.config.ts` and every file under `hubspot/`, and reports everything that is wrong in one pass. It never touches the network, so run it after every edit, in a pre-commit hook and first in CI.

## Usage

```sh
kalup validate [--target <name>] [--json]
```

## Options

| Option | What it does | Default |
| --- | --- | --- |
| `--target <name>` | Also check that this target is declared in `kalup.config.ts`. | Not checked |
| `--json` | Print one [`envelope/1`](/docs/reference/json-output) document to stdout and nothing else. | Human output |

## What it does

1. Finds the project: the nearest directory, from the current one upwards, that holds `kalup.config.ts`.
2. Reads `kalup.config.ts` and every `.ts` file under `hubspot/`. The files are parsed as data and never run. See [Config files](/docs/config/config-files) for the grammar.
3. Builds the IR, the document every other command works from, and checks it against the rules below.
4. Prints a one-line verdict, then one line per issue.

Errors make the config invalid. Warnings do not: they are printed and the command still exits 0.

What it checks, in short:

| Area | Checks |
| --- | --- |
| Grammar | Only builders, literals and comments on their own line. No spreads, variables, calls or computed keys. |
| Builders | Known `p.<kind>` builders, allowed chain calls (`.strict()` on enums, `.required()`, `.readonly()`, `.managed(false)`), and `.strict()` with options. |
| Properties | `fieldType` fits the builder, `group` exists, keys are unique per object, no managed `hs_` or `a<digits>_` names, `lifecycle` is consistent. |
| Custom objects | A name and labels HubSpot takes. A warning when a display, required or searchable field names a property the object file does not list. |
| Addresses | Every group, property and custom object has exactly one definition. |
| Targets | Every target has a positive integer `portalId`, no target is named `config`, override keys are real addresses. |
| Warnings | Names without the project `prefix`, `p.json` outside a `textarea`, IDs from another target that no address maps to. |

## Output

A valid project:

```text
$ kalup validate
Config valid (0 errors, 0 warnings)
```

An invalid one. The verdict goes to stdout, each issue to stderr as `file:line: CODE: message (fix: ...) (docs: ...)`:

```text
$ kalup validate
Config invalid (1 error, 0 warnings)
hubspot/objects/companies.ts:33: E_TYPE_FIELDTYPE: fieldType 'text' is not allowed for p.number (type number) (fix: use one of 'number') (docs: errors/E_TYPE_FIELDTYPE.md)
```

### With --json

`data` holds the verdict and the counts. `issues` holds every error and then every warning.

```json
{
  "format": "envelope/1",
  "ok": false,
  "data": {
    "valid": false,
    "counts": { "errors": 1, "warnings": 0 }
  },
  "issues": [
    {
      "code": "E_TYPE_FIELDTYPE",
      "message": "fieldType 'text' is not allowed for p.number (type number)",
      "file": "hubspot/objects/companies.ts",
      "line": 33,
      "configPath": "Company.properties.seatCount.fieldType",
      "fix": "use one of 'number'",
      "docs": "errors/E_TYPE_FIELDTYPE.md"
    }
  ]
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `data.valid` | boolean | `true` when there are no errors. Warnings do not count. |
| `data.counts.errors` | number | Issues whose code starts with `E_`. |
| `data.counts.warnings` | number | Issues whose code starts with `W_`. |

## Exit codes

| Code | When |
| --- | --- |
| 0 | No errors. There may be warnings. |
| 1 | No `kalup.config.ts` here or above (`E_NO_CONFIG`), or a usage error. |
| 3 | At least one error. |

See [Exit codes](/docs/reference/exit-codes).

## Errors

| Code | When | Fix |
| --- | --- | --- |
| [`E_NO_CONFIG`](/docs/reference/errors#e_no_config) | No `kalup.config.ts` in this directory or any above it. | Run `kalup init --portal <id>` in the project directory. |
| [`E_NOT_DATA`](/docs/reference/errors#e_not_data) | Something outside the grammar: a spread, a variable, a call, an unknown field, a wrong value type. | Write plain `key: value` entries. The fix names the exact problem. |
| [`E_UNKNOWN_BUILDER`](/docs/reference/errors#e_unknown_builder) | `p.<kind>` is not a builder, for example `p.text`. | Use the builder for the HubSpot type and put the field type in `fieldType`. |
| [`E_BAD_CHAIN`](/docs/reference/errors#e_bad_chain) | A chain call other than `.strict()`, `.required()`, `.readonly()` or `.managed(false)`, one used twice, or `.strict()` on a builder other than `p.enum` and `p.multiEnum`. | Use one of the four, once each. |
| [`E_MISSING_EXPORT`](/docs/reference/errors#e_missing_export) | A file under `hubspot/` has no `defineObject` or `defineCustomObject` export, or one under `hubspot/pipelines/` no `definePipeline` export. | Add the export, or move the file out of `hubspot/`. |
| [`E_UNSUPPORTED_FILE`](/docs/reference/errors#e_unsupported_file) | A file in the wrong place, such as a `definePipeline` export outside `hubspot/pipelines/`. | Move it where the fix says. |
| [`E_PIPELINE_FIELD`](/docs/reference/errors#e_pipeline_field) | A stage's metadata field belongs to another object, or a probability is outside 0 to 1. | Use the field of the pipeline's object. See [Pipelines](/docs/config/pipelines). |
| [`E_PIPELINE_ID`](/docs/reference/errors#e_pipeline_id) | A pipeline or stage ID HubSpot would refuse: too long, holding whitespace or `/`, or used twice. | Give one of the two another ID. |
| [`E_PIPELINE_STAGES`](/docs/reference/errors#e_pipeline_stages) | A pipeline with no stage, or a ticket pipeline with no closed stage. | Add a stage, or mark one `ticketState: 'CLOSED'`. |
| [`E_DUPLICATE_LABEL`](/docs/reference/errors#e_duplicate_label) | Two stages of a pipeline, or two pipelines of an object, share a label. | Give one of the two another label. |
| [`E_OBJECT_FIELD`](/docs/reference/errors#e_object_field) | A custom object name or label HubSpot would refuse: a name that does not start with a letter, holds other than letters, digits and underscores, or is over 50 characters; a label over 50. | Choose a name HubSpot takes, or shorten the label. |
| [`E_DUPLICATE_ADDRESS`](/docs/reference/errors#e_duplicate_address) | One address is defined twice. | Keep one definition. |
| [`E_DUPLICATE_KEY`](/docs/reference/errors#e_duplicate_key) | A key, export name or internal name used twice where it must be unique. | Remove or rename one. |
| [`E_DUPLICATE_OPTION`](/docs/reference/errors#e_duplicate_option) | An enum lists the same option value twice. | Remove one of the two options. |
| [`E_DUPLICATE_ALIAS`](/docs/reference/errors#e_duplicate_alias) | Two options of one enum share an alias: an `as`, or the value of an option without one. | Give one of them another `as`. |
| [`E_REFERENCE_DEFINITION`](/docs/reference/errors#e_reference_definition) | A property is neither a full definition nor a valid reference. | Add `label`, `group` and `fieldType`, or drop the definition. |
| [`E_STRICT_WITHOUT_OPTIONS`](/docs/reference/errors#e_strict_without_options) | `.strict()` on an enum that lists no options. | List the options, or drop `.strict()`. |
| [`E_TYPE_FIELDTYPE`](/docs/reference/errors#e_type_fieldtype) | `fieldType` does not fit the builder. | Use a field type the fix lists. |
| [`E_UNKNOWN_GROUP`](/docs/reference/errors#e_unknown_group) | `group` names a group the object does not declare. | Add the group to the object's `groups` block. |
| [`E_KEY_COLLISION`](/docs/reference/errors#e_key_collision) | Two exports of one object use the same key. | Rename one key. The internal name stays. |
| [`E_HS_PREFIX`](/docs/reference/errors#e_hs_prefix) | A managed property's internal name starts with `hs_` or `a<digits>_`, prefixes HubSpot reserves for its own and an integration's properties. | Rename it, or drop the definition to reference the property. |
| [`E_LIFECYCLE`](/docs/reference/errors#e_lifecycle) | A `lifecycle` block contradicts itself. | Follow the fix. |
| [`E_PORTAL_ID`](/docs/reference/errors#e_portal_id) | A target has no `portalId`, or it is not a positive integer. | Set the Hub ID from the HubSpot account menu. |
| [`E_TARGET_NAME`](/docs/reference/errors#e_target_name) | A target is named `config`. | Rename the target. |
| [`E_UNKNOWN_OVERRIDE`](/docs/reference/errors#e_unknown_override) | An override key is not an address in config. | Use an address `kalup ir` lists. |
| [`E_DEFAULT_TARGET`](/docs/reference/errors#e_default_target) | `defaultTarget` names a target that is not declared. | Use a declared target, or remove `defaultTarget`. |
| [`E_UNKNOWN_TARGET`](/docs/reference/errors#e_unknown_target) | `--target` names a target that is not declared. | Use a declared target or declare it. |

Warnings (exit 0): [`W_PREFIX`](/docs/reference/errors#w_prefix), [`W_JSON_FIELDTYPE`](/docs/reference/errors#w_json_fieldtype), [`W_UNRESOLVED`](/docs/reference/errors#w_unresolved), [`W_OBJECT_PROPERTY`](/docs/reference/errors#w_object_property).

## Examples

Check the whole project:

```sh
npx kalup validate
```

Also check that a target exists before a script uses it:

```text
$ kalup validate --target staging
Config invalid (1 error, 0 warnings)
kalup.config.ts:9: E_UNKNOWN_TARGET: target 'staging' is not declared (fix: use one of sandbox, production, or declare targets.staging) (docs: errors/E_UNKNOWN_TARGET.md)
```

In CI, fail the job on any error:

```sh
npx kalup validate --json > validate.json
```

The step fails on exit 3, and `validate.json` holds the issues for a comment or an artifact.

## For agents

- Run `kalup validate --json` after every edit to a file under `hubspot/` or to `kalup.config.ts`, before anything else.
- Branch on the exit code, not on the text: 0 means go on, 3 means fix the issues and run it again.
- Each issue has `file`, `line`, `configPath` and `fix`. Apply the `fix`, then validate again. Do not guess past it.
- Warnings arrive in `issues` with `ok: true`. Tell them apart by the `W_` prefix. Report them to the user, but they do not block.
- Never work around `E_NOT_DATA` by moving logic into the file. The files are data on purpose. See [Working with AI agents](/docs/guides/working-with-agents).
