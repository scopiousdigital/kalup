# Identity spike: a server-assigned ID and a cross-target reference

`plan/1` and `kalup.state/1` can carry a resource whose ID HubSpot assigns and a reference that resolves to a different ID on each target, with no change to either schema. The one gap it found in them is closed: `normVersions` was a closed object with no room for a new resource type, and on 2026-09-28 it became a map keyed by type (property, group and object stay required), so the first new type needs no `plan/2`. A second limit is in `ir/1`: it cannot hold a new reference field on an existing type, so the scenario tested here, a property that refers to a list, could not come from config without `ir/2`. References in the definitions of new types fit. The verdict covers `plan/1` and `kalup.state/1`; see item 2 below for `ir/1`.

ADR 0016 and ADR 0021 asked for this proof before the contracts are declared sufficient for broader resources. It was run on 2026-09-28, offline, as a contract test: [`packages/cli/test/spike/identity.test.ts`](../../packages/cli/test/spike/identity.test.ts). It uses the real `validatePlan`, `validateState`, `validateIR` and `stableStringify` from `@kalup/core`, and the CLI's approval digest (`writesHash`, `approvalContext`) and saved-plan parser (`parsePlan`, apply's first check). No product code for lists was added, and nothing touched HubSpot.

## What was tested

- A test-only resource type `list` with bound identity: HubSpot assigns a numeric ID on create, and a person can rename the list in the UI. The address is `list:renewals_due`.
- A test-only property, `property:companies/renewal_queue`, whose definition refers to the list: `sourceList: { $ref: 'list:renewals_due' }`.
- Two targets, `north` (portal 5550001) and `south` (portal 5550002). The list has ID `4412` in north and `9981` in south.

## What holds

1. **State binds the address per portal.** Each portal's `kalup.state/1` file has an entry for `list:renewals_due` whose `id` is that portal's ID, `4412` or `9981`. The editable name is a unit of the base (`base.name`), like any other owned field. Both files validate.
2. **The plan binds, the step stays logical.** Each target's plan carries `bindings: { "list:renewals_due": { "id": "4412" } }` (or `9981`), and the property step's `desired` keeps `{ "$ref": "list:renewals_due" }`. The steps of the two plans are the same bytes and hold no portal ID. Both plans validate against `plan/1` and pass apply's offline check.
3. **The digests differ only through the binding.** The two approval contexts differ in `destination`, `state` and `bindings`, and nowhere else. Give south's plan north's destination and state, and the binding alone keeps the digests apart; give it north's binding too, and the digests are equal.
4. **A rebind voids the approval.** North's plan with south's list ID, with a new ID for a list recreated in north, with no binding, or sent to south's portal: each has another `writesHash`, so neither `--approve` nor the terminal confirmation of the original covers it, and the edited file left with its old digest is refused with `E_PLAN_DIGEST`.
5. **A planned create stays logical until apply records the ID.** On a portal with no state, a plan that creates the list and the property has no binding for the list: the list keeps its logical identity, and the property's `desired` holds the `$ref`. The list's create is at risk `risky` with the note "if it was renamed in HubSpot, run kalup bind", as architecture section 4 requires, and `plan/1` carries both. The state apply would then save records the ID HubSpot returned in the list's entry, and the property's base keeps the `$ref`. The next plan binds `{ "id": "9981" }`, and that binding is part of its digest.

## What the contracts could not express

1. **`plan/1` could not record a normalizer version for a new type (closed on 2026-09-28).** `normVersions` is a closed object with `group`, `object` and `property`. A plan that compared lists has nowhere to say which list normalizer it used, so apply could not refuse a plan made under another one (`E_PLAN_VERSION`). Adding `list` to a closed object is a new field, which [the compatibility policy](../compatibility.md) makes a new format version. `normVersions` is now a map from resource type (a lowercase name) to a positive integer, keeping the three current types required, and apply refuses a plan whose map names a type this version has no normalizer for (`E_PLAN_VERSION`). The approval digest already covered `normVersions` whole, so the digest did not change.
2. **`ir/1` cannot hold a new reference inside an existing definition.** A `list` resource fits `ir/1`: a resource's `type` is an open string, and the definition of a type the schema does not describe is an open object. But a property definition is closed, so `sourceList` on a property is `unexpected field "sourceList"`. Real references mostly sit in the definitions of new types, such as a workflow that enrolls from a list or a list that filters on a property, which `ir/1` leaves open. A new reference field on a property, group or custom object is a new IR version.
3. **Two descriptions need a sentence each; the shapes do not change.** The state schema describes `id` as "the portal name the entry owns", and architecture section 5 says an entry owns a resource when `id` equals the name its address resolves to. For a bound type, `id` holds the assigned ID and ownership means that ID exists in the portal. The plan schema describes a binding's `id` as a custom object's type ID; for a bound type it is the resource's assigned ID. Both schemas already accept these values.

## What a real adapter would still need

- **Live verification** for the type, recorded like the [HubSpot reference](hubspot-reference.md): the ID's form on create and on read, whether a rename keeps the ID, what a create returns, read-after-write lag, and the scopes.
- **A resolver**: `toPortal` at apply (an ID created earlier in the run, then the state binding) and `toLogical` at pull, with a `RefSite` catalog of where IDs sit in each payload.
- **A `bind` command**, and the name chain from architecture section 4: exactly one live resource with the same name plans `adopt`, several are blocked `ambiguous` with the `bind` fix, none plans a `create` at risk `risky`.
- **Apply support**: record the ID a create returns, check before each write that the bound ID still exists (as `E_BINDING_CHANGED` does for custom objects), a registry row with identity `bound`, and write allowlist entries. Trusted derivation must also rate a create of a bound type with no binding as `risky`: stated risk is outside the approval digest and `--yes` relies on the derived risk, but `stepRisk` in `derive.ts` rates any create with no state owner `safe`, so a plan that states `safe` would pass `--yes` and could create a duplicate of a renamed list.
- **Recovery**: `state rebuild` and `target rebind` find natural resources by key. A bound resource has no key to find it by, so they need the name chain or `bind`.
