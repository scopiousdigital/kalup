Introduce the Kalup CLI for managing HubSpot configuration as code, with typed configuration exports, an oclif command layer, structured JSON output and shipped command/error documentation.

- Read existing properties, property groups and custom object schemas into TypeScript with `init` and `pull`. Validate configuration, print its IR, format it canonically and inspect portal access with `status`. Configuration is parsed without executing project code; importing `defineConfig` never starts the CLI.
- Compare config, portals and scoped snapshots with `compare`; save observations with `snapshot`; generate Markdown data dictionaries with `docs`. Coverage distinguishes missing, unreadable, unsupported and excluded resources. Incomplete comparisons fail instead of reporting equality, and difference checks include semantic changes that do not rewrite a file.
- Select a portal with `--target`, `defaultTarget`, the sole configured target or an interactive choice. Automation and JSON output require an unambiguous selection. Target names are user-defined; the portal ID is checked against the credential before use.
- Preserve explicit field ownership, aliases, comments and lifecycle settings during formatting and pull. Validate the complete candidate project before saving it. Reject duplicate enum identities, duplicate physical-resource mappings and invalid custom-object declarations. Report codec mismatches, shadowed names and unsupported address coverage explicitly; some portal internal names cannot be represented in configuration.
- Plan against per-portal state, classifying config changes, drift, conflicts and divergence. Hold differing values by default, support explicit `--take config` intent, and report missing resources and orphans. Adoption and base updates are visible effects. Tombstones express destruction or ownership release; removing a definition never deletes a portal resource.
- Preserve overall and per-object property limits for standard and custom objects. Exhausted limits block affected creates; insufficient headroom warns. Live and archived property reads cover the supported sensitivity lists. Unreadable limits remain explicitly recorded rather than interpreted as subscription entitlements.
- Apply saved plans for properties and groups, or plan and apply an unprotected target in one run. Saved-plan validation covers destination, policy, state lineage/serial, bindings, versions, expected live values and approval effects. Custom object schemas are observed and compared but not written.
- Require terminal confirmation, a bounded `--yes` approval for safe work on an unprotected target, or `--approve <writesHash>` with the documented reviewed-CI credential custody. Deletes always require a person at a terminal. `allowDestroy` is false by default.
- Coordinate local execution by portal, persist state atomically and journal requests. Execute serially, recheck preconditions and verify read-back. Writes with uncertain outcomes are never blindly resent. Partial execution exits 5 and recovers through a new plan, which warns when the last apply did not finish; repeated completed execution is recognized.
- Bound read requests with timeouts and retries. Keep structured values exact while escaping JSON controls and sanitizing human text, Markdown and issue paths. Ignore credential files during project initialization and keep tokens out of output and local history.

The packages remain pre-release. Plan and state formats have changed during development and are not yet a stable compatibility promise. Live conformance and release validation are tracked separately from implementation.
